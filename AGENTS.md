# AGENTS.md — Гід «Стяг незламних»

Ці інструкції діють для всього проєкту. Гід допомагає ветеранам, ветеранкам, людям з інвалідністю внаслідок війни та їхнім родинам зрозуміти, що робити далі й куди звернутися. Загальноукраїнські процедури доповнюють контакти Одещини. Гід працює як вебзастосунок (PWA) та нативний застосунок для iOS і Android. Базові сценарії доступні офлайн.

## Карта проєкту

| Ділянка | Де працювати |
| --- | --- |
| Вебінтерфейс | `index.html`, `styles.css`, `app.js` і `assistant.js`. Звичайні HTML, CSS і JavaScript без етапу збирання. |
| Мобільний інтерфейс | `mobile/src/app/` — екрани Expo Router. `mobile/src/guide.tsx`, `search-field.tsx` і `route-actions.tsx` — спільні компоненти в `mobile/src/`. |
| Каталог | `catalog.js` — джерело маршрутів, контактів, чек-листів і посилань. Веб читає його напряму. `mobile/src/data/catalog.json` генерується для мобільної збірки. |
| Пошук і підбір маршруту | `mobile/src/search.js` використовується вебом, мобільним застосунком і сервером. `mobile/src/search.d.ts` описує його контракт для TypeScript. |
| Закладки й відмітки | Веб використовує `localStorage` в `app.js`. Мобільний застосунок зберігає прогрес у SQLite через `mobile/src/guide-state.tsx` і `route-progress.ts`. |
| Сервер і доставка PWA | `server.cjs` обслуговує локальний запуск та опційний `/api/assistant`. `sw.js` відповідає за офлайн кеш. `wrangler.toml` і `.assetsignore` визначають статичну публікацію на Cloudflare. |

Загальний запуск описано в [README](README.md). Вимоги до інструментів і сценарії на пристрої є в [мобільному README](mobile/README.md). Збирання, підпис і публікація описані в [інструкції випуску](docs/store-release.md).

## Як вносити зміни

1. Знайдіть поточну реалізацію, її виклики та найближчий приклад у коді. З’ясуйте, чи зміна стосується спільних даних, обох клієнтів або лише однієї платформи.
2. Для виправлення знайдіть причину й усуньте її в місці, яке вже відповідає за цю поведінку. Врахуйте старі закладки, відмітки, посилання та збережені налаштування.
3. Доведіть зміну до звичного сценарію користувача. Якщо змінили контракт, оновіть виклики, типи, відповідні дані та документацію разом. Збережіть сторонні зміни у робочій папці.
4. Підсумуйте, що змінилось, які перевірки фактично виконано й що залишилось неперевіреним.

## Стандарти коду

- **KISS.** Обирайте найпростіше повне рішення. Використовуйте наявний компонент, функцію чи API платформи. Додавайте залежність, коли вона дає конкретну користь, яку складно отримати наявними засобами.
- **YAGNI.** Додавайте лише можливості, потрібні для поточної задачі. Майбутні провайдери, режими, прапорці й шари залишайте до появи конкретного сценарію.
- **SOLID.** Тримайте відображення, пошук, збереження і роботу з мережею на їхніх наявних межах. Давайте функціям і компонентам одну чітку відповідальність, передавайте лише потрібні дані й зберігайте контракт для чинних викликів. Вводьте інтерфейс або адаптер, коли є реальна потреба взаємозамінювати реалізації чи ізолювати зовнішню залежність.
- **DRY.** Тримайте спільні дані й однакові правила в одному місці. Веб і мобільний клієнт можуть мати власний код відображення там, де цього потребує платформа.
- Дотримуйтеся стилю сусіднього коду. Використовуйте зрозумілі назви й типи, обробляйте збої на межах із мережею та сховищем. Коментар має пояснювати причину рішення, якщо її не видно з коду.

## Дизайн-система обов’язкова

Перед будь-якою зміною інтерфейсу прочитайте [дизайн-систему](docs/typography.md). Це стосується нових екранів і дрібних змін у кнопках, полях, підписах та станах. Використовуйте наявний компонент або стиль, одну із семи типографічних ролей, чинні кольорові токени, відступи й розміри.

Зберігайте спільну ієрархію і поведінку вебу й мобільного застосунку. Враховуйте нативні вкладки й шторки, мобільні світлу й темну теми, великий текст, фокус клавіатури, доступні назви контролів і зони натискання. Якщо змінюєте спільний патерн чи токен, узгодьте обидві реалізації та оновіть дизайн-систему в тому самому наборі змін. Платформний виняток коротко опишіть у ній.

## Каталог, контент і «Характерник»

- Пишіть інтерфейс і довідкові матеріали простою українською. Починайте маршрут із конкретної дії. Звіряйте умови, строки, суми, контакти й посилання з першоджерелом відповідальної установи та оновлюйте дату фактичної звірки. Рішення щодо заяви ухвалює установа. [Правила оновлення джерел](docs/official-sources.md).
- Редагуйте дані в `catalog.js`. Після змін згенеруйте мобільний знімок командою `npm --prefix mobile run sync:catalog`. Зберігайте стабільними ідентифікатори маршрутів, розділів і пунктів, якщо немає запланованого переходу для наявних посилань і прогресу.
- «Характерник» бере тексти, цифри, контакти й посилання з каталогу. У мережевому режимі модель лише добирає ідентифікатори маршрутів або розділів. Перевіряйте їх за каталогом і зберігайте локальну відповідь на випадок збою чи відсутності мережі. У мобільних збірках для магазинів підбір відбувається на пристрої.
- Зберігайте API ключі на сервері. Значення `EXPO_PUBLIC_*` доступні у клієнтській збірці. Зберігайте історію запитань у пам’яті сеансу. Зміни в обробці запитань мають відповідати публічному опису приватності в `privacy.html`.

## Команди та перевірки

Команди нижче запускаються з кореня проєкту. Для вебу використовуйте Node.js 20 або новіший. Для мобільної частини використовуйте версію з `engines` у [mobile/package.json](mobile/package.json).

| Завдання | Команда |
| --- | --- |
| Запустити PWA локально | `node server.cjs`, потім відкрийте `http://localhost:4173`. |
| Встановити мобільні залежності з lockfile | `npm --prefix mobile ci` |
| Оновити мобільний знімок каталогу | `npm --prefix mobile run sync:catalog` |
| Перевірити знімок, типи та поведінку пошуку, контактів і прогресу | `npm --prefix mobile run check` |
| Запустити потрібну мобільну платформу | `npm --prefix mobile run ios` або `npm --prefix mobile run android` |

- Для змін каталогу, пошуку або мобільної логіки використовуйте `check`. Для вебінтерфейсу відкрийте змінений сценарій у браузері. Для спільної поведінки перевірте обидва клієнти. Для нативних змін звірте потрібні сценарії з розділом [«Перевірка на пристрої»](mobile/README.md#перевірка-на-пристрої).
- Після зміни ресурсів, що кешуються, оновіть `CACHE_NAME` у `sw.js`. Якщо змінюєте `?v=` у посиланнях, узгодьте їх з `APP_FILES` у `sw.js`. Якщо додаєте публічний файл, перевірте списки `.assetsignore` та `publicFiles` у `server.cjs`. Перевіряйте роботу офлайн після завантаження PWA з мережею, а перший запуск мобільного застосунку офлайн — у збірці з вбудованим JS.
- Перед регенерацією мобільних нативних проєктів звірте й збережіть ручні налаштування підпису та інтерфейсу. Перед публікацією звірте конфігурацію, збірку й стан випуску з [інструкцією випуску](docs/store-release.md). Виконуйте деплой, завантаження в магазин або подання на перевірку за запитом користувача.
